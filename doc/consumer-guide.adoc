= Consumer guide: selecting a review charter
:toc: left
:toclevels: 2
:icons: font

How a repository owner opts a cuioss repository in to a review charter assembled from its own
declaration, opts it in to the second, code-review pass, and checks that each took effect.

== Before you start

The repository must already be reviewed by cuioss-review-bot: a caller workflow calls
`cuioss/cuioss-organization/.github/workflows/reusable-cuioss-review-bot.yml` at org release
`v0.30.0` or later. Without an opt-in, that reviewer applies the central charter from this
repository's `.pr_agent.toml`, and nothing on this page is required to keep it working.

== What you select

The assembled charter has three parts, always in this order:

. *The spine* — `packs/spine.md`, the cross-cutting security and correctness charter. It is always
applied first. It cannot be selected, deselected or replaced.
. *Domain packs* — the packs you list, in the order you list them. Each carries one domain's rules.
. *Additional rules* — the repository's own rule sentences, appended after the last pack.

A pack key is the file name of a pack under
https://github.com/cuioss/cuioss-review-bot/tree/main/packs[`packs/`] without `.md`; that directory
is the only list of published keys, and each pack names the domain it covers in its opening paragraph.
`spine` is not a pack key. The keys starting with `code-review-` belong to the code-review pass and
are selected under `code_review:` only — see xref:#code-review-pass[The code-review pass].

Read the packs you intend to select before you enable them: a pack's rules are reported as findings
on every pull request.

== Declaring it

Add the block to `.github/project.yml` on the repository's *default branch*:

[source,yaml]
----
cuioss-review-bot:
  enabled: true
  packs:
    - python
    - plugin
  additional_rules: []
----

* `enabled` — only `true` assembles. Keep it a boolean.
* `packs` — a list of pack keys. Never list `spine`.
* `additional_rules` — a list of strings, each one rule sentence naming the mechanism a diff breaks.
The rules are appended after the packs; they cannot remove, replace or precede the spine. Leave the
list empty when the packs cover the repository.

Land the change through its own reviewed pull request. The reviewer reads the declaration from the
default branch, never from the pull request under review, so the pull request that adds the block
is still reviewed with the charter in force before it, and the new charter applies from the first
pull request reviewed after it merges.

== The four states of `enabled`

[cols="2,3"]
|===
|Declaration |Charter the review uses

|No `cuioss-review-bot:` block, or no `.github/project.yml`
|The central charter.

|The block without `enabled`
|The central charter. Absence is never consent.

|`enabled: false`
|The central charter.

|`enabled: true`
|The spine, then each listed pack, then `additional_rules`.
|===

Disabled always means the central charter, never no charter.

[#code-review-pass]
== The code-review pass

The code-review pass is a second, independent review that runs beside the security review, as the
separate check `review / code-review`. It reviews against the code-review charter —
correctness, error handling, resource lifecycle, duplication, documentation accuracy, test quality
and contract drift — and publishes its own comment. See xref:charter.adoc#category-ceiling[Category
ceiling] for why it is a separate pass.

[IMPORTANT]
====
Do not add a `code_review:` block until the repository's caller workflow pins a
`cuioss/cuioss-organization` release that supports it: a release after `v0.41.0`, whose
`reusable-cuioss-review-bot.yml` carries the `code-review` job and pins its `workflow-scripts/` to
the same release. The declaration script of `v0.41.0` and earlier accepts only `enabled`, `packs`
and `additional_rules` under `cuioss-review-bot:`, so it rejects `code_review` as an unknown key and
fails the review of every pull request. Until the caller's pin moves, the pass is inert.
====

=== Declaring it

Nest a `code_review:` block inside the `cuioss-review-bot:` block, on the default branch:

[source,yaml]
----
cuioss-review-bot:
  enabled: true                # the security pass, unchanged
  packs: [python, plugin]
  additional_rules: []
  code_review:
    enabled: true
    packs:
      - code-review-python
      - code-review-plan-marshall-plugin-dev
      - code-review-documentation
    additional_rules: []
----

* `enabled` — only `true` runs the pass. Keep it a boolean.
* `packs` — a list of full pack keys, each starting with `code-review-`, in the order they are
applied. Never list `code-review-spine`: it is always applied first. An empty or absent list runs
the pass on `code-review-spine.md` alone.
* `additional_rules` — a list of strings appended after the packs, the code-review counterpart of
the outer `additional_rules`. The outer list is not applied to this pass.

The code-review charter is `packs/code-review-spine.md`, then each listed pack, then this block's
`additional_rules`.

The block is independent of the outer `enabled`. A repository can run the code-review pass beside
the central security charter by declaring `code_review:` with `enabled: true` and leaving the outer
`enabled` absent or `false`.

As with the outer block, the declaration is read from the default branch, so it takes effect from
the first pull request reviewed after the change merges.

=== The states of `code_review.enabled`

[cols="2,3"]
|===
|Declaration |Effect

|No `code_review:` block, no `cuioss-review-bot:` block, or no `.github/project.yml`
|No code-review pass. The `review / code-review` job still runs: it logs one line naming the
declaration state that skipped the pass, skips its remaining steps, and ends green.

|The block without `enabled`
|No code-review pass. Absence is never consent.

|`enabled: false`
|No code-review pass.

|`enabled: true`
|The pass runs on the code-review spine, then each listed pack, then the block's
`additional_rules`.
|===

Every state but `enabled: true` behaves like the first row. Unlike the security pass, the
code-review pass has no central fallback: disabled means no code-review pass, and a green
`review / code-review` check alone does not show that the pass ran.

=== What fails the code-review pass

Both review jobs read the declaration with the same script, so a `code_review:` block that cannot
be honoured fails the security `review` job and the `review / code-review` job alike, each with an
error naming the cause. The block is validated whether or not it is enabled:

* `code_review:` is not a mapping, or carries a key other than `enabled`, `packs` and
`additional_rules`;
* `enabled` is not a boolean;
* `packs` or `additional_rules` is not a list of strings;
* a pack key does not start with `code-review-`, or is `code-review-spine`;
* with `enabled: true`, a code-review pack (or the code-review spine) does not exist under
`packs/`, cannot be fetched, or is empty.

Every failure under xref:#what-fails-the-review[What fails the review] fails both jobs the same
way.

When the pass runs, the `review / code-review` job also fails when the model produced no review,
or when the publisher cannot find a `## PR Code Review Guide 🧭` comment carrying this run's review
or updated during the run — see xref:workflow-integration.adoc#code-review-pass[The code-review
pass].

=== Re-running it with `/review`

A `/review` comment re-runs both passes. In a repository that runs the code-review pass, that job
accepts a plain `/review` only, in any case and optionally followed by free words such as
`/review please look at the parser`. It fails with one `::error::` ending `Comment a plain
'/review' to review both passes` when the comment carries any option token, quoted or not — for
example `--config.publish_output=true` or `-i` — or is not a `/review` command, as `/reviewer` is
not. Options are refused because PR-Agent applies them after the workflow's settings, where they
could switch the pass's publishing back on over the security review or change its charter.

`/review -i` (incremental review) therefore fails the `review / code-review` job, while the
security job still runs it. Comment a plain `/review` to review both passes.

[#what-fails-the-review]
== What fails the review

The review job fails, with an error naming the cause, instead of falling back to the central
charter, when the declaration cannot be honoured. The `review / code-review` job reads the same
declaration and fails with it:

* `cuioss-review-bot:` is not a mapping, or carries a key other than `enabled`, `packs`,
`additional_rules` and `code_review`;
* `enabled` is not a boolean;
* `packs` or `additional_rules` is not a list of strings;
* a pack key does not exist under `packs/`, cannot be fetched, is `spine`, or starts with
`code-review-` (code-review packs are listed under `code_review.packs` only);
* the `code_review:` block cannot be honoured — see xref:#code-review-pass[The code-review pass];
* the composed charter is empty;
* `.github/project.yml` is not valid YAML or repeats a mapping key;
* the file carries a top-level `pr-agent:` block, whatever it declares.

A legacy `pr-agent:` block is the retired name of this block. Rename the key to
`cuioss-review-bot:`; everything under it keeps its meaning.

== Checking that it took effect

Open the reviewer job of a pull request reviewed after the declaration landed, and expand the
`Assembled review charter` group of the declaration step. Its title names the spine, the packs in
order and the number of additional rules, and its body is the exact text the reviewer received. On
the central path the log instead names the central charter and the declaration state that selected
it.

For the code-review pass, open the `review / code-review` job and expand the `Assembled code-review
charter` group of its declaration step. Its title names `code-review-spine`, the packs in order and
the number of additional rules, and its body is the exact text that pass received. On the pull
request the pass publishes its own persistent comment, headed `## PR Code Review Guide 🧭`, beside
the security review's `## PR Reviewer Guide 🔍`; each pass updates only its own comment.

A green `review / code-review` check does not by itself mean the pass ran. If the declaration step
instead logs a single `Code-review charter: none — the code-review pass is skipped` line naming a
declaration state, and the pull request carries only the security comment, the pass did not run:
check the declaration on the default branch. A pull request with no `review / code-review` check at
all is reviewed through a release that predates the pass: check the caller's pin.

The job's schema and every failure path are specified in
https://github.com/cuioss/cuioss-organization/blob/main/docs/project-yml-schema.adoc[`project-yml-schema.adoc`];
the workflow side is described in xref:workflow-integration.adoc#charter-assembly[Charter assembly].

= Workflow integration
:toc: left
:toclevels: 2
:icons: font

What the organization's reusable workflow
https://github.com/cuioss/cuioss-organization/blob/main/.github/workflows/reusable-cuioss-review-bot.yml[`reusable-cuioss-review-bot.yml`]
does around PR-Agent, and why each part lives there rather than in `.pr_agent.toml`.

== Skip rules

[cols="2,3"]
|===
|Rule |Reason

|Skip `dependabot[bot]` pull requests
|Dependency bumps are gated by CI and auto-merge.

|Skip `cuioss-release-bot[bot]` pull requests
|Consumer propagation and workflow-reference bumps.

|Skip any pull request labelled `skip-bot-review`
|The shared organization-wide opt-out label.

|Skip fork pull requests
|Secrets are unavailable to them, so the token step could only fail.
|===

The rules are job-level `if:` guards in the reusable workflow. PR-Agent's own `ignore_pr_labels`,
`ignore_pr_authors`, `ignore_pr_title`, `ignore_pr_source_branches` and `ignore_pr_target_branches`
are read only by `should_process_pr_logic()` in its webhook servers; the GitHub Action runner never
calls it. Setting them in `.pr_agent.toml` would parse, appear in the resolved configuration, and
review every pull request anyway. A guarded-out pull request consumes no runner minutes and no
tokens.

The guard is evaluated when a review is triggered: on `opened`, `reopened` and `ready_for_review`.
Apply `skip-bot-review` at creation time or before marking a draft ready; a label added after a
review was posted does not retract it.

A `/review`, `/improve`, `/describe`, `/ask` or `/help` comment from an owner, member or collaborator
runs regardless of the label, because someone asked on purpose. Bot senders are excluded, so the
reviewer cannot trigger itself off its own comment.

== `.plan/**` is not reviewed

`.plan/` holds plan-marshall's machine-generated orchestration records. Two mechanisms keep it out
of reviews:

* The workflow's `changes` job skips the whole review — the security job and the code-review job
alike — when every changed file is under `.plan/`.
* `[ignore] glob = [".plan/**"]` in `.pr_agent.toml` removes `.plan/` files from a mixed diff.
`filter_ignored()` is called inside `GithubProvider.get_diff_files()`, so the filtered hunks never
reach the model. This is a different code path from the dead `ignore_pr_*` keys above.

== Image pinned by digest

PR-Agent's action is a Docker action whose Dockerfile is `FROM pragent/pr-agent:github_action`, a
floating tag. Pinning the action by commit would pin the wrapper while the executed code moves. The
reviewer steps therefore use the image digest directly:

[source,yaml]
----
uses: docker://pragent/pr-agent@sha256:<digest>
----

The `docker://` form does not accept the action's `artifact_path` / `artifact_instructions` inputs;
they map to the `ARTIFACT_PATH` / `ARTIFACT_INSTRUCTIONS` environment variables if ever needed.
Digest bumps are a deliberate, reviewed change to the reusable workflow.

== Reviewer identity

The reviewer posts as the `cuioss-review-bot` GitHub App, not as `github-actions[bot]`. Downstream
review ingestion, including plan-marshall's `automatic-review`, attributes findings by author login,
so a shared identity would file unrelated workflow comments as review findings.
`cuioss-release-bot` is not reused because it is on the skip list: sharing it would entangle who
authored a pull request with who reviewed it.

App permissions: pull requests read/write, issues read/write, contents read-only, metadata
read-only. The reviewer never pushes, and `[config] restricted_mode = true` withholds only the
`push_code` capability, which neither `/review` nor `/improve` uses.

== Vertex AI credentials across the container boundary

`google-github-actions/auth` exchanges the job's OIDC token for short-lived credentials of the
reviewer service account. Two boundaries are crossed by hand, and getting either wrong produces an
authentication failure inside the reviewer that shows no review and no obvious error:

* *Path.* The auth action writes its credentials file into `$GITHUB_WORKSPACE` and reports a host
path. The reviewer container mounts the workspace at `/github/workspace`, so the workflow passes
`/github/workspace/<basename>`.
* *Environment.* A Docker action receives only the variables named in its own `env:` block, so
`GOOGLE_APPLICATION_CREDENTIALS` is restated on each reviewer step.

[#charter-assembly]
== Charter assembly

The reviewer runs one of two mutually exclusive steps:

* *central charter* — no `PR_REVIEWER.EXTRA_INSTRUCTIONS` in its environment, so the charter in
`[pr_reviewer] extra_instructions` of `.pr_agent.toml` applies;
* *assembled charter* — the same step plus `PR_REVIEWER.EXTRA_INSTRUCTIONS` carrying a charter
composed for the repository under review.

Before either runs, the workflow reads the repository's `.github/project.yml` from its *default
branch* through the contents API, never from the pull request head, so an author cannot change the
rules that review their own change. Only a `cuioss-review-bot:` block with `enabled: true` selects
the assembled step. The charter is then composed in a fixed order: `packs/spine.md`, each pack the
block lists under `packs:` in the listed order, then the block's `additional_rules`. Every other
state keeps the central charter.

A declaration that cannot be honoured fails the job with an `::error::` naming the cause, before
either reviewer step runs: an unreadable file, malformed YAML, an unknown key, a non-boolean
`enabled`, an unknown or unfetchable pack, `spine` or a `code-review-` key listed under `packs:`, an
empty composition, a duplicated key, a legacy top-level `pr-agent:` block, or a `code_review:` block
that cannot be honoured (see xref:#code-review-pass[The code-review pass]). The code-review job runs
the same declaration step and fails with it.

The composed charter is echoed into the run log as an `Assembled review charter` group naming the
spine, the packs in order and the number of additional rules. On the central path the log names the
central charter and the declaration state that selected it.

Two steps exist because GitHub Actions cannot drop an `env:` key conditionally, and an empty
`PR_REVIEWER.EXTRA_INSTRUCTIONS` would replace the central charter with nothing.

The consumer side of the declaration is described in xref:consumer-guide.adoc[Consumer guide].

[#code-review-pass]
== The code-review pass

The second, code-review pass runs as a separate job, `code-review` (check `review / code-review`),
in parallel with the security `review` job. Both depend only on the `changes` job, and each has its
own fail-closed gate and its own persistent comment.

=== When the job runs

The job's `if:` guard copies the security job's `pull_request` arm term for term: the fork,
`dependabot[bot]`, `cuioss-release-bot[bot]` (and `{owner}-release-bot[bot]`) and `skip-bot-review`
skip rules, and the `changes` job's `.plan/**`-only skip. A pull request guarded out there shows
both checks as skipped. Of the comment commands it admits `/review` alone, under the same gate on
who may trigger it, so a `/review` comment re-runs both passes; `/improve`, `/describe`, `/ask` and
`/help` stay with the security job.

Within those rules the job always runs: whether the pass is wanted is decided by its declaration
step, not by the guard. A repository that declares no `code_review:` block with `enabled: true` —
including one that declares nothing at all — gets a `code-review` job that reads the declaration,
logs one line naming the declaration state that skipped the pass, skips every later step, and ends
green. No Google Cloud authentication and no reviewer run take place.

=== Comment-triggered runs

On a comment-triggered run PR-Agent executes the comment as its command line and applies every
`--section.key=value` token *after* the step's environment, so `/review --config.publish_output=true`
would switch publishing back on and overwrite the security review's comment, and other tokens could
rewrite the code-review charter. When the pass runs on a comment, a step before the reviewer,
`Refuse a /review comment carrying options` (`workflow-scripts/check-code-review-command.py`),
therefore admits a plain `/review` only. It tokenizes the comment the way the pinned PR-Agent does,
case-insensitively, and fails the job with one `::error::` ending `Comment a plain '/review' to
review both passes` when:

* the first token is not `/review` — another command, `/reviewer`, or an empty comment;
* any later token is an option, quoted or not — `--config.publish_output=true`, `-i` and every other
`-` or `--` token;
* the comment cannot be tokenized.

Free words after the command, as in `/review please look at the parser`, are accepted; `/review`
ignores them. `/review -i` (incremental review) is refused like any other option, so in a
repository that runs the pass it fails the `review / code-review` job while the security job runs
it as before. The step does not run on `pull_request` events, nor when the pass is not declared.

=== Its charter

The declaration step reads the same default-branch `.github/project.yml` with the same script as
the security job's declaration step, and takes the script's code-review outputs. Only a
`code_review:` block with `enabled: true` runs the pass, independently of the outer `enabled`. The
charter is composed in a fixed order: `packs/code-review-spine.md`, each pack listed under
`code_review.packs` in the listed order, then `code_review.additional_rules`. With no packs listed
the charter is `code-review-spine.md` alone. The composed charter is echoed into the run log as an
`Assembled code-review charter` group naming `code-review-spine`, the packs in order and the number
of additional rules.

Because both jobs run the same declaration script over the same file, a declaration that cannot be
honoured fails *both* jobs with the same `::error::`. That includes a `code_review:` block that
cannot be honoured, whether or not it is enabled: a non-mapping block, an unknown key, a non-boolean
`enabled`, a `packs` or `additional_rules` that is not a list of strings, a pack key without the
`code-review-` prefix or naming `code-review-spine`, and — when enabled — a code-review pack that is
unknown, unfetchable or empty. A `code-review-` key under the outer `packs:` fails both jobs as
well; the two passes' packs never mix.

=== Its reviewer step

The step runs the same pinned image with the same App token and Vertex AI credentials as the
security step, and reads the same `.pr_agent.toml`, including the shared `[pr_reviewer]` section.
Its environment is the central reviewer step's with four named exceptions — see
xref:configuration-precedence.adoc#environment-variables[Environment variables outrank this file]:

* `PR_REVIEWER.EXTRA_INSTRUCTIONS` carries the code-review charter;
* `github_action_config.auto_describe` and `github_action_config.auto_improve` are literal `false`,
so the pass runs `/review` only, whatever the caller's inputs and labels ask of the security job;
* `CONFIG.PUBLISH_OUTPUT` is `false`, so PR-Agent produces the review without posting it. PR-Agent
re-applies environment overrides after merging every `.pr_agent.toml`, so no settings file can turn
publishing back on.

`require_security_review` is not overridden, so the code-review comment keeps PR-Agent's
security-concerns row.

=== Its publisher

PR-Agent renders every `/review` under `## PR Reviewer Guide 🔍` and locates its persistent comment
by that header, so a second pass publishing through PR-Agent would overwrite the security review's
comment. The code-review step therefore publishes nothing. A publisher step,
`workflow-scripts/publish-code-review.py` in `cuioss/cuioss-organization`, runs in the same pinned
image whenever the reviewer step wrote a `review` output: it renders that output with PR-Agent's own
renderer, replaces the header with `## PR Code Review Guide 🧭`, and publishes it as a persistent
comment of its own, created or updated in place, under the `cuioss-review-bot` App identity. The two
headers share no prefix, so neither pass can find or update the other's comment.

PR-Agent's persistent-comment call swallows its own failures, so the publisher does not trust it.
It reads the pull request's comments back and reports success only when a comment opens with
`## PR Code Review Guide 🧭` and either

* carries exactly the review this run rendered, once PR-Agent's `(Code review updated until commit
…)` line is set aside and line endings are normalized — a re-run on an unchanged commit renders
identical text, and GitHub need not move `updated_at` for an edit that changes nothing; or
* was created or updated at or after the job's start.

It fails when no comment carries the header, or when the only one has other content and an older
`updated_at`. A match on the security review's `## PR Reviewer Guide 🔍` comment never counts.

=== Its fail-closed gate

The code-review job ends with its own gate, the security gate applied to this pass. Its oracle is
the same — the reviewer step's structured `review` output, never a published comment — and so is
its scope: reviewed `pull_request` actions with `auto-review` on, and `/review` comments. It fails
when that output is absent. Unlike the security gate, it also fails when the publisher did not
confirm a `## PR Code Review Guide 🧭` comment carrying this run's review or updated during this
run, because this pass always publishes. The gate
runs only when the pass runs; a repository without the pass never reaches it.

[#fail-closed-gate]
== Fail-closed gate

This section describes the security `review` job's gate; the code-review job's gate is described
under xref:#code-review-pass[The code-review pass].

PR-Agent's GitHub Action runner catches its own exceptions and exits 0, so a run whose every model
call failed reports success. The workflow ends with a gate whose oracle is the reviewer step's
structured `review` output: `pr_reviewer.py` writes it from `_prepare_pr_review()` before the
publish decision, so it exists whenever the model produced a review and is absent whenever every
model call failed. The gate reads whichever reviewer step ran.

The gate covers pull request runs on the reviewed actions and `/review` comments. It is not
extended to `/improve`, which writes a separate `improve` output. A published comment is not used
as the oracle: a clean review may publish nothing depending on configuration, and the persistent
review comment is updated in place, so a stale one would satisfy an existence check.

== A clean review is published

`[pr_reviewer] publish_output_no_suggestions = true`, so the reviewer comments even when it found
nothing. Without it a clean review and a total failure look the same at the pull request, and a
consumer that counts the reviewer's comments as participation cannot see a reviewer that agreed.

`final_update_message = false` keeps that to one comment: the upstream default posts a second
"Persistent review updated to latest commit" comment on every refresh, which carries no review
content and would be filed as a finding by comment-collecting consumers.

== Tools

[cols="1,1,3"]
|===
|Tool |Automatic |Configuration

|`/review`
|yes
|Caller input `auto-review`, default `true`.

|`/describe`
|no
|Caller input `auto-describe`, default `false`. It rewrites the pull request description, which
collides with generated pull request bodies and the machine-readable blocks automation reads from
them.

|`/improve`
|per pull request, or per repository
|Runs on a pull request labelled `cuioss-review-bot-improve`, or on every pull request when the
caller sets `auto-improve: true`. Tuned in `[pr_code_suggestions]` of `.pr_agent.toml`.
|===

The three toggles are the deliberate exception to central configuration: they are caller inputs, so
a repository changes them without editing this repository. On-demand commands work as pull request
comments in every adopting repository regardless of the toggles.
